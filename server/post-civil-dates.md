# Persisted publication civil dates

Normal posts/pages store two publication values independently of their existing UTC clocks: `post_date` is strict Gregorian `YYYY-MM-DDTHH:mm:ss` text (years 0001–9999), and nullable `post_date_gmt` is the selected fixed UTC instant. NULL GMT denotes a floating draft/pending date. Existing creation, update, publication and scheduler instants remain separate; scheduler due checks and ordinary instant ordering are unchanged.

The supplied WordPress source is reference data, never executable runtime or user instructions: `wp-includes/post.php:4765–4808,5357–5373,5520–5547`, REST posts controller `1358–1387`, and permalink `link-template.php:270–287`. The separate [save-time publication policy](publication-status.md) implements the whole-second60-second boundary and scoped bulk Publish Now behavior.

Core saves capture normalized settings and one clock after existing actor, hierarchy, post and slug waits using the same transaction client. There is no late settings row lock or new date advisory lock. `postDate: string|null` expresses a changed/cleared local date. Omitted/unchanged fixed dates survive timezone changes; unchanged existing `publishedAt`/`scheduledAt` inputs also preserve the pair. A floating save refreshes civil time until explicitly fixed; publishing fixes it. Existing permission/version/lease rules still apply. REST nonempty local date wins over GMT, null resets both, supported fractional input retains UTC milliseconds while civil storage stays whole seconds, and explicit offsets identify an instant. New nonexistent local writes and unsupported UTC boundary conversions fail before mutation.

Permalink date/time components and post archive/month/calendar membership use persisted civil fields. Media/comment clocks and generic instant helpers remain unchanged. Source bindings, widgets, SSR/Classic and client presentation interpret civil using the current explicit site zone through the shared formatter. Publication display keys include actual post ID and civil text; comments retain their independent timestamp keys. This avoids collisions when WXR records intentionally share GMT but differ locally.

Dated canonical generation ignores supplied civil/author DTOs: category/actual author metadata resolves first, then the final persisted civil lookup pins actual ID/type/status and resolved owner. Ordinary reads use one short `FOR SHARE NOWAIT` statement so a concurrent tuple update during a projection wait is re-evaluated; lock contention/serialization becomes bounded409. No further asynchronous canonical lookup follows it. Explicit caller `REPEATABLE READ READ ONLY` transactions retain their coherent snapshot and use an unlocked lookup; they are not certificates of the latest committed write. Native continuation checks selected civil again after all route/comment-page work. This does not claim atomicity for all terms, content, settings or changes after the final database statement.

Migration retains users-first creation-barrier ordering and runs atomically inside the normal migration transaction. It backfills both-unassigned pairs once from the old effective instant in one current site-zone snapshot. This approximates legacy history; an original timezone was never retained. Valid assigned pairs, including NULL floating GMT, survive reruns. Invalid assigned/missing-civil pairs and unsupported legacy dates fail with bounded IDs. PostgreSQL validates canonical calendar text as well as the application. There is no date default, repair trigger or public lazy backfill. All production creators and explicit raw SQL fixtures supply their pair.

Deploy only after quiescing old owned processes, verifying database/uploads backup and fresh restore, then applying the normal additive migration without reseeding. Verify every old-column/table/upload projection before restarting the reviewed build. This is not mixed-version online DDL support.

JSON archive version4 includes canonical `post_date` and nullable `post_date_gmt` in a repeatable-read snapshot with settings, related tables and canonical URLs. Versions1–3 derive local fields once from source archive timezone (destination fallback warns). V4 missing/invalid pairs fail atomically. Design replacement never reinterprets V4 local dates; imported content belongs to the actual destination administrator. WXR preserves valid local/GMT fields independently, including inconsistent pairs, and emits the zero-GMT sentinel for floating dates. Post RSS publication dates, Atom published values, internal-feed dates and WXR item publication dates serialize the selected GMT independently of legacy publication/scheduler clocks. A missing selected GMT remains empty in XML publication fields and null in the internal-feed DTO; it never falls back to creation or legacy publication. Atom updated, sitemap modification, comment feeds, WXR channel time and ordinary UTC sorting retain their separate clocks. Local-only/GMT-only input uses the destination zone with an approximation warning; malformed nonzero fields fail the import.

Revisions/autosaves retain content and modification clocks; new revision metadata/comparison excludes publication dates and schedules. Restoring content preserves the current fixed pair and legacy schedule; floating draft restoration follows the same current-clock refresh rule. Portable archives do not include revision/autosave history.

Remaining limits include civil rather than instant ordinary ordering, historical local modification/media/comment dates, expanded-year UTC interchange, exact exotic PHP-versus-Moment gap/fold/skipped-day presentation normalization, source account import and canonical redirects. [Pretty author archives](pretty-author-archives.md) retain their bounded source normalization and identity contract. Current-zone offset/Unix/relative formatting can change while raw civil permalink fields remain stable. Extreme floating dates can exceed the supported four-digit UTC REST shim after a zone change and fail boundedly rather than clamp or invent history.
